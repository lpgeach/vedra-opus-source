## Done

- **Fetching:** `scripts/fetch-ffmpeg.mjs` (`npm run fetch:ffmpeg`).
  - It downloads BtbN `autobuild-2026-11-13-12-43`, ffmpeg `n8.1.3-35-gf1acb0a266`, LGPL shared, for Linux x64 and Windows x64.
  - It checks the SHA-256: mine matched the digest GitHub reports for the Linux file.
  - It keeps only ffmpeg, ffprobe, their libraries, `LICENSE.txt` and a `SOURCE.txt`, in `vendor/ffmpeg/<os>-<arch>/`, which git ignores.
  - On macOS it says there is no build and exits.
- **Packaging:** electron-builder copies that folder to `resources/ffmpeg` on Linux and Windows. `npm run package` fetches first. CI fetches before tests in the verify and browser jobs.
- **Main (`src/main/media/`):** finding the tools (override, packaged, vendor), probing, running with progress, and the decisions:
  - MP3 is kept;
  - other sound becomes MP3;
  - WebM VP8/VP9 is remuxed, giving it a seek index and length;
  - other video becomes VP9/Opus WebM;
  - each video gets a PNG poster frame.
- **Where the pipeline is used:**
  - `importAsset` and `storeRecording` run media through it when ffmpeg is there. Converted assets keep the author's name with the new extension, plus duration and picture size.
  - A file ffmpeg cannot read is refused with the reason.
  - Without ffmpeg, everything behaves as before, with one console warning.
- **Renderer:**
  - imports add a video's poster too, and Insert → Video… sets it;
  - insertion uses the length the pipeline measured;
  - the status bar shows "Converting … %".
- **Docs:**
  - `docs/licences.md`: ffmpeg's LGPL v3 obligations and how each is met or not yet, the patent note and the minimal-build recommendation, and the SCORM schema licences.
  - The brief `docs/briefs/P6.3-media-pipeline.md`.
  - README and `development.md` (fetch once), an AGENTS table row, PLAN ticked with what is outstanding.
- **Tests:**
  - `main/media/media.test.ts`: 6 pure tests, plus 6 integration tests with the real ffmpeg on inputs ffmpeg makes itself, and a check that ffmpeg is there on Linux and Windows.
    - The integration tests cover: WAV to MP3 with its length; MP3 kept byte for byte; mp4 to VP9/Opus WebM with size and poster; a recorded WebM without cues or length remuxed to have both; a narration recording stored as MP3; an unreadable file refused.
  - Player: a pipeline-remuxed WebM plays from its trim start to its trim end, in Firefox too (it stuck there in P6.2).
  - e2e:
    - an imported WAV shows as MP3;
    - a recording is stored as MP3. The P6.1 test expected `.webm` and was updated for the new behaviour (rule 11);
    - an mp4 becomes WebM with its poster set, and plays when published.

## Mistakes this session, and what changed

- **Node's `cpSync` on library symlinks.** My first fetch script used `cpSync(..., { dereference: true })` on the versioned symlinks, which failed in Node 26 (EISDIR) and left a half-filled folder. Fixed with `copyFileSync`, which follows links. Recorded in pitfall #89.
- **An anchor that missed after Prettier.** One scripted edit to the audio e2e spec stopped on an anchor that Prettier had re-wrapped. Rule 1 caught it: nothing was written, and I re-read the text.
- **A missing log entry from session 37.** It did not add P6.2 to the skills file's evolution log; added now.

## Follow-up: H.264 and AAC (branch `fix/linux-patent-codecs`)

Luke asked whether importing H.264 or AAC needs a licence. As far as I know, yes in principle: patent licences cover decoding too. That is not legal advice; it is recorded in `docs/licences.md`. Converting on import keeps courses clean, but the conversion itself has to read the file.

Luke's decision:

- **Linux:** refuse H.264 and AAC imports, as the free DaVinci Resolve does.
- **Windows and macOS:** read them through the operating system's own licensed decoders, later.

Saved to memory.

- **Done:**
  - `refusePatented` in `planFor`, set on Linux in `main/index.ts`. The import is refused with "uses H.264 and AAC, which Vedra Opus cannot import on Linux. Convert it to WebM … first."
  - Tests: a unit test (each format, the option on and off); an integration test (an H.264/AAC mp4 refused, a VP9/Opus mp4 converted); an e2e test (the refusal message on Linux, nothing imported).
  - The existing mp4 e2e test now uses VP9/Opus inside mp4, so it converts on every platform.
  - Docs: `docs/licences.md`, the P6.3 brief, PLAN's outstanding note, pitfall #89.
- **Verified:** `typecheck` and `format:check` pass; `npm test` 500 passed; the audio and video e2e specs pass (5, with the Linux-only test run here). The full e2e suite was not rerun: nothing else imports mp4 or m4a.

  - Windows still reads H.264/AAC through the prebuilt ffmpeg until then.
