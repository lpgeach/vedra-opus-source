## Done

- **Brief** `docs/briefs/P2.3-object-renderers.md`, written first.
- **`packages/render`**: `renderObject`, `renderLayer`, `renderSlide` — pure functions from model objects to a `RenderNode` (plain data). Back ends: `toMarkup` (escaped HTML string) and `toDom`.
  - Shapes: rectangle, rounded rectangle, ellipse, triangle, line, arrow, polygon. Fill: none, solid, gradient, image. Outline: colour, width, solid/dash/dot. Shadow. Opacity. Rotation.
  - Images: fill the frame; crop; opacity; a neutral placeholder when the file is missing.
  - Buttons: rounded rectangle with the button's appearance and a label.
  - Groups: a container of their children.
  - Text boxes, shape text and button labels draw **plain text only**, provisionally (`text.ts`). P2.4 replaces this.
- **`packages/model`**: twelve polygon presets in `shapes.ts` (diamond, pentagon, hexagon, octagon, star, right triangle, parallelogram, trapezoid, chevron, block arrow, plus, callout) and object factories in `factory.ts`. No change to the saved format.
- **Visual tests**: 45 cases in `packages/render/visual/objects.spec.ts`, run in Chromium, Firefox and WebKit against one shared set of 44 reference images. New scripts `npm run test:visual` and `test:visual:update`; new CI job `Visual` on Linux.

## Decisions

Recorded in the brief. The ones most likely to matter later:

- The renderer returns data, not DOM or React, so the player does not ship React and output can be unit tested without a browser.
- Lines and arrows run along the horizontal middle of their frame; rotation gives direction.
- There is no "fit" setting for images. The plan's "crop and fit" is met by crop plus the frame; adding a fit mode would change the saved format and nothing needs it yet. **Luke may want to revisit this.**
- A group's own rotation is not applied by the renderer; P2.2 must rotate the children's frames when a group is rotated.
- States are not applied by the renderer yet (P4.1).

## Found by the tests

- **Chromium and Firefox drew an SVG picture used as a shape fill differently.** Chromium letterboxed it, Firefox covered the shape. The first reference image (from Chromium) was the wrong one. The renderer now computes the placement itself when the picture's size is known, and both engines agree. See skills/project-specific.md #20.
- A horizontal line vanished because an SVG with zero height draws nothing (#21).

## A test changed, and why

`packages/model/src/history.test.ts`, "undo/redo invariant": given an explicit 60-second time limit. It runs 300 random edit sequences and takes about five seconds alone; with more test files running in parallel it began failing with "Test timed out in 5000ms" (never with a counterexample). The assertions and the number of runs are unchanged. See #22.

## Not verified

- **WebKit was never run locally.** Its system libraries are not available on this machine (#19). It passed in CI on the first attempt.
- Visual tests run on Linux only. That macOS and Windows browsers draw the same is assumed, not tested.
- **No text is covered by a visual test**, including button labels and shape text. Text is checked only structurally, in unit tests.
- Bitmap pictures (PNG, JPEG) in visual tests: the test picture is an SVG. Bitmap fills use the same placement code when the size is known, and the browser's own "cover" when it is not; the second path has a unit test but no visual test.
- Very large or very small sizes, extreme rotations, and performance with many objects.
- **Nothing in the app uses the renderers yet.** They are proven by tests only until P2.2 puts them on the stage.
