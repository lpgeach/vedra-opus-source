## Why

R1 (session 105) made our ffmpeg free of patented codecs on every system, so Windows refused H.264/AAC as Linux and macOS did. Luke asked whether Windows and macOS should accept H.264. They should, through the decoders the systems license themselves, as planned on 2026-11-17. He chose to build the helpers (`docs/briefs/R3-os-decoders.md`).

## What was done

- **`vo-decode`, our own small program,** built beside ffmpeg by `scripts/build-decoder.sh`, which `npm run fetch:ffmpeg` runs. On a checkout that has ffmpeg it builds only the helper.
  - **Windows:** C with Media Foundation's source reader (`apps/desktop/native/decoder/windows/decoder.c`), cross-compiled with mingw-w64 in WSL, 415 KB. It imports only Windows' own DLLs (checked).
  - **macOS:** Swift with AVFoundation's asset reader (`apps/desktop/native/decoder/macos/main.swift`), 51 KB.
  - **Three commands:**
    - `info` (JSON: duration, the picture and sound the system can decode, and the tracks it cannot);
    - `audio` (16-bit WAV);
    - `video` (YUV4MPEG2 4:2:0 on standard output, at a constant frame rate: each frame time shows the latest frame decoded by then).
- **The pipeline** (`main/media/system-decoder.ts`): when a file would be refused and the helper is there, `info`, then the WAV, then `video` piped into our ffmpeg. That makes WebM (VP9, Opus), or MP3 for sound alone, turned upright by the rotation, and tagged with the colour standard (BT.709 from 720 lines). A track the system cannot read is refused, saying so. The poster, probing and storing are as before. PowerPoint's media and recordings use the same path.
- **Linux** has no helper and refuses as before.
- **CI** builds and caches the helper with ffmpeg (not run).
- **Docs:** `docs/licences.md` (Windows and macOS read through their own decoders), `docs/development.md`, pitfall #158, the handover.

## Found on the way

- **The first Windows picture was green above and coloured below.** Media Foundation's frames were taller than the picture, and it said so with a "media type changed" flag after the first frame, which the helper ignored. It now reads the layout again then, and takes the plane height from the buffer's length. The colours were then right (seen against ffmpeg's test pattern).
- **Rotation:** ffmpeg's `display_rotation 90` comes out as 270 from both systems: degrees to turn clockwise. The test compares our upright frame with ffmpeg's own upright frame of the same picture in VP9 (difference < 20 of 255), and against the other turn (> 40).
- **1080p:** a 1080p H.264/AAC clip made by macOS's own encoder (`avconvert`; not kept in the repository) decoded through both helpers to the right picture. Windows took 5 s for 3 s of video. Both decoders gave the same values for the clip's green bar, which `avconvert` had colour-shifted, so the helpers pass on what is in the file. The WebM is now tagged BT.709 for HD, as ffmpeg's own path keeps a source's tags.

## Not verified

- **A real phone video:** the tests use our fixture and a clip made by `avconvert`.
- **Variable frame rate, HDR, and more than two sound channels:** macOS takes them down to stereo; on Windows, Media Foundation chooses.
- **H.265 on Windows:** it needs Microsoft's HEVC extension, and was not tried.
- **The helpers in a packaged and signed app.**
- **Apple Silicon.**
