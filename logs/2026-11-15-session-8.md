## Done this session

Step 1, all working in the app with tests:

- The slide is drawn on the stage with `@vedraopus/render`, through a React adapter (`stage/RenderTree.tsx`).
- Insert: shapes (a gallery of 18), text box, button, picture from disk, picture from the media list. New objects land in the middle of the stage, selected, cascading if the spot is taken.
- Select: click, shift-click to add or remove, marquee, Select All, Escape or a click on empty stage to clear. Clicking inside a group selects the group.
- Move (Shift keeps to one axis), resize from eight handles (Shift keeps proportions, Alt resizes about the centre; pictures keep proportions from a corner unless Shift is held), rotate (whole degrees, Shift for 15° steps). Lines have only their two end handles.
- Several objects, and groups, move, resize and rotate together.
- Arrow keys nudge by 1 (10 with Shift). Delete removes.
- Every drag is one undo step. Escape cancels a drag and leaves nothing to undo. Autosave waits until a drag ends.
- Zoom: Fit, stepped zoom in and out, Ctrl+wheel about the pointer, Ctrl+0 / + / −. Pan: scroll, middle-button drag, Space+drag.
- Edit menu Undo, Redo, Delete and Select All now act on the document (or on the text field, when typing in one).
- Status bar shows how many objects are selected.

## Where this stopped

Two things are open. **Do the first before anything else.**

### 1. An unverified fix for a failing macOS test — check this first

CI on `wp/p2.2-stage` is **red on macOS** (green on Linux, Windows and the Visual job). One test fails: `e2e/stage.spec.ts`, "zoom changes the size on screen but not the document; Ctrl+wheel zooms about the pointer". Ctrl+wheel should keep the stage point under the pointer where it is; on macOS it ended about a pixel off.

Two causes were found:

- **The test measured wrongly.** Wheel events report the pointer in whole pixels, but the test aimed at a fractional position. Fixed in the test: it now parks the pointer on a whole pixel and works out the stage point from that.
- **A real bug in `Stage.tsx` `onWheel`.** One wheel turn arrives as several events. Re-reading the stage point under the pointer for every event lets errors build up (scroll positions are whole pixels, and a stage smaller than its area is centred and cannot follow the pointer). At a 1440×900 window this reached 9 pixels. The first fix kept the first event's stage point for 250 ms; that broke whenever events came more slowly than that.

**The last commit replaces the 250 ms timer** with: the gesture continues while the pointer has not moved, the zoom is still the one last asked for (`getEditorState().zoom === last.zoom`), and nothing else has scrolled the stage (`placedScroll` and the viewport's `onScroll`). The test also now pauses 400 ms inside the burst to cover slow machines.

**That last commit was typechecked and linted but its tests were NOT run** — the session was stopped first. So:

1. `npm run e2e` and see whether the zoom test passes locally.
2. Check it at a macOS-sized window, where the bug showed. In a throwaway test, after `launchApp()`, call `app.evaluate(({ BrowserWindow }) => BrowserWindow.getAllWindows()[0].setSize(1440, 900))`, then do what the zoom test does and print how far the point moved. It should be under half a pixel at 1440×900, 1600×700, 1280×800 and 1024×728, with and without 400 ms pauses between wheel events. Delete the throwaway test afterwards.
3. Push and confirm CI is green on all three systems (`gh run list --branch wp/p2.2-stage`).

If the new logic is wrong, the behaviour to aim for is in the comment above `continuing` in `onWheel`.
