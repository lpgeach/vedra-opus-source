## Why

The plan is built and reviewed. Luke asked for the release work that needs neither CI nor accounts: the third-party notices page in the app, and the source offer for what we ship. The source offer raised a choice, which Luke made.

## Luke's decisions (2026-11-23)

- **The source offer:** our own minimal LGPL ffmpeg on Linux and Windows too, from the same pinned sources as macOS, replacing BtbN's prebuilt builds. BtbN's builds statically link about 80 libraries, several of them LGPL, so their complete corresponding source would be about 80 pinned repositories, several GB a release. Ours is seven archives. It also takes out the H.264 and AAC code, as `docs/licences.md` recommended before a public release.
- **Windows refuses H.264/AAC, as Linux and macOS do,** until a later helper reads them through Windows' own licensed decoders (Media Foundation).

The work is in two parts: R1, our builds (this branch, `docs/briefs/R1-own-ffmpeg-builds.md`); then R2, the notices page and the source offer.

## What was done

- **The H.264/AAC fixture:** `fixtures/media/h264-aac.mp4`, 4.5 KB, made with BtbN's build just before it was retired (`fixtures/media/README.md`). Our builds cannot make another.
- **WSL:** `mingw-w64` installed (Ubuntu's package, 13.0.0), for the Windows cross-build.
- **`scripts/build-ffmpeg.sh <mac|linux|win> <out>`** replaces `build-ffmpeg-macos.sh` (`docs/briefs/R1-own-ffmpeg-builds.md`):
  - the same sources as macOS, plus zlib 1.3.1 (ffmpeg's PNG encoder needs it, for posters; macOS had used the system's);
  - `--disable-autodetect`, so nothing of the build machine's is picked up;
  - no capture or output devices (only `lavfi`, which the tests use);
  - its own checks: what each build loads, that it runs, VP9 with Opus, MP3 and PNG made, and no H.264, H.265 or AAC encoder or decoder.
- **`npm run fetch:ffmpeg`** runs it on every system, through WSL on Windows (`wslpath` for the paths).
- **The app refuses patented formats on every system** (`refusePatented: true`); the message names Windows, macOS or Linux.
- **Tests:** the media samples are VP9/Opus everywhere; the refusal unit test and e2e use the fixture on every system; CI cross-builds Windows' ffmpeg in a Linux job and caches each system's build by the script's hash (not run: no CI).
- **Docs:** `docs/licences.md` (the ffmpeg section rewritten), `docs/development.md` (what each system needs), the P6.3 brief, `docs/HANDOVER.md`, pitfall #153.

## What the builds needed (found on the way)

- **`--pkg-config-flags=--static`:** the libraries are static, so ffmpeg's link tests need their own dependencies (`-lm`, pthreads). Without it, configure said "opus not found" on Linux and found no libvpx decoders on Windows.
- **Linux run paths:** ffmpeg's configure evaluates extra flags once, and make expands the libraries' link line twice. `$ORIGIN` therefore needs `\$\$` for the programs and `\$\$\$\$` for the libraries; the first try gave the shell's process number. The script now checks both with `readelf`.
- **Windows:** libavdevice's webcam capture imported `AVICAP32.dll`, and libvpx's pthreads `libwinpthread-1.dll`. Devices are off, and the runtime is linked statically (`-static`). The script checks that every DLL imports only Windows' own DLLs and ours.
- **macOS:** bash 3.2 calls an empty array unbound under `set -u` (the `HOST` options are a plain word now). configure linked CoreFoundation, CoreVideo and CoreMedia into every library with nothing using them; `-dead_strip_dylibs` drops them, and the script checks that only our libraries and `libSystem` are linked.
