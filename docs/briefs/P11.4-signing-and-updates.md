# P11.4 Signing and auto-update

**Plan:** "macOS Developer ID signing and notarisation, Windows code signing, `electron-updater` with a release channel; Linux AppImage update."

**Luke's decision (2026-11-22, session 98): build it signing-ready.**

- The signing and update wiring is driven by environment variables, and tested with certificates made for the test.
- It works the moment real certificates and accounts are added.
- No real certificate is used or needed now.

Built in two parts, each on its own branch. The plan's box is ticked after part B. There is no saved-format change.

## Part A: signing (`wp/p11.4a-signing`)

**Windows** (electron-builder's own signing, configured):

- `CSC_LINK` (a `.pfx` file or base64) and `CSC_KEY_PASSWORD` sign the app's executables and the installer, SHA-256 only, with the publisher's name.
- Timestamping uses the certificate authority's server for a real release. `ELECTRON_BUILDER_OFFLINE=true` turns it off for a test build, so nothing leaves the machine.

**macOS:**

- hardened runtime, with an entitlements file of our own: JIT for V8, the microphone for narration, and library validation off so the bundled ffmpeg and LibreOffice, signed separately, can run;
- the Developer ID identity from `CSC_LINK`/`CSC_NAME`;
- notarisation through electron-builder when `APPLE_API_KEY`, `APPLE_API_KEY_ID` and `APPLE_API_ISSUER` (or the Apple ID trio) are set, and skipped when they are not.

**Linux:** AppImage and deb are not signed (as is usual); part B covers AppImage updates.

**`npm run check:signing`** (`scripts/check-signing.mjs`) proves the wiring on Windows without a real certificate:

1. makes a throwaway code-signing certificate with OpenSSL;
2. packages the app (`--dir`) with it, offline;
3. checks every executable is signed by that certificate (`Get-AuthenticodeSignature`);
4. removes the certificate.

On macOS it signs ad hoc and checks `codesign --verify` (in the headless VM, with the LibreOffice for macOS work).

**`docs/releasing.md`** says, for Luke:

- which variables to set for a real release on each system;
- what each certificate or account is;
- how to check a signed build.

**Tests:**

- unit: the builder config holds the settings above (read from `electron-builder.yml`);
- the signing check, run on Windows this session, with its output in the log.

**As built (session 100):**

- `electron-builder.yml`:
  - Windows: `signtoolOptions` with the publisher, SHA-256 only and a timestamp server;
  - macOS: hardened runtime and `signing/entitlements.mac.plist` (`build/` is git-ignored here, so the entitlements live in `signing/`).
- `npm run check:signing` passed on Windows.
  - OpenSSL (from Git for Windows) made the certificate, with older PKCS#12 encryption that every Windows tool reads.
  - Every executable in the package was signed: the app's, and the bundled ffmpeg's and LibreOffice's. LibreOffice's own signatures are replaced by ours.
  - `Vedra Opus.exe` reports `CN=Vedra Opus Test Signing`, sha256RSA.
  - electron-builder downloaded its signing tools (winCodeSign) from GitHub on the first run: a build tool, not shipped.
- `packaging.test.ts` pins the signing settings and checks the config holds no secret.
- `docs/releasing.md` is written for Luke: what each certificate and account is, the variables, and how to check.
- **Not done here:**
  - the macOS check (codesign in the VM), which comes with the LibreOffice for macOS work;
  - a real certificate;
  - an app icon (electron-builder uses Electron's default and says so).

## Part B: updates (`wp/p11.4b-updates`)

- **`electron-updater`** (pure JavaScript, no native code), with GitHub releases of this repository as the feed.
- **A release channel** in the app's settings: Stable or Beta.
- **Off by default:**
  - an update check contacts a server, and Vedra Opus sends nothing anywhere unless the author asks;
  - Help → Check for Updates… checks once;
  - Help → "Check for Updates Automatically" (off until ticked) checks at start and daily;
  - development builds never check;
  - the privacy e2e stays as it is: nothing leaves the machine by default.
- **When an update is found:** the author is told, and chooses whether to download it. Once downloaded, it is installed when the app quits, or at once if they choose.
- **Per system:**
  - Windows (NSIS) and macOS (zip, signed) update in place;
  - Linux AppImage updates in place;
  - a deb install is told where to download.
- **Tests:**
  - unit: the update logic with a fake updater (off by default, the channel, the choices, dev builds never checking);
  - e2e: Check for Updates… against a feed served on localhost (`latest.yml` of a newer version), which says an update is available. Nothing is downloaded.

**As built (session 101):**

- `electron-updater` 6.8.11 (pinned) is a runtime dependency. Its `autoUpdater` is wrapped by `Updates` (`main/updates.ts`), which tests drive with a fake.
  - It never downloads or installs unasked: `autoDownload` and `autoInstallOnAppQuit` are off until the author chooses.
  - It never goes back to an older version.
- **The Help menu:** Check for Updates…, Check for Updates Automatically (a checkbox), and Update Channel (Stable, Beta).
  - The settings are in `settings.json` (`updates.automatic`, `updates.channel`); older files read as off and Stable.
  - Beta sets `allowPrerelease`.
- **Active only in a packaged app.** A development build says "Updates are checked in installed copies of Vedra Opus."
  - The e2e gives a feed with `VEDRAOPUS_UPDATE_FEED` (a generic feed, `forceDevUpdateConfig`).
- **Automatic checks** run at start and then daily, and speak only when there is an update. A check the author asked for always says what it found.
- **A Linux install that is not an AppImage** (a deb) is told of a new version and offered the releases page.
- **The feed:** `publish` in `electron-builder.yml` names this repository's GitHub releases; with no token, it reads public releases.
- **Found on the way:** electron-updater adds a cache-busting query to each feed request; the e2e's server matches the path alone.
