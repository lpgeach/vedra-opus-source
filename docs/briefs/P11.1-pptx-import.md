# P11.1 PowerPoint import

**Plan:** "Parse PPTX: slides, masters and layouts, text, shapes, images, notes, basic animations and transitions mapped to ours; unsupported content rasterised with a report."

An author who has a PowerPoint deck starts a course from it. File → Import PowerPoint… reads a `.pptx` and opens a new, unsaved project made from it, and a report says what came across and what did not. The import reads the file's XML itself; there is no copying from PowerPoint, and no saved-format change.

The package is built in four parts, each on its own branch and merged on its own. The plan's box is ticked after part D.

## Decisions (Luke, 2026-11-22)

- **Unsupported content is drawn as pictures by LibreOffice, bundled with the app.**
- **Only the part of LibreOffice the import needs is bundled,** not the whole suite (part D).

## Part A: the reader (`wp/p11.1a-pptx-reader`)

In main (`apps/desktop/src/main/import/pptx/`), as pure functions from the file's parts to a `Project`, with `yauzl` and the model's XML reader. A deck whose parts cannot be read is refused with a reason.

**Size and units:**

- The project's stage is the deck's slide size (`p:sldSz`), at 96 pixels an inch: 9525 EMU a pixel, so a 16:9 deck is 1280 × 720.
- Text sizes are points times 4/3.

**The theme:**

- `dk1`, `lt1` and `accent1`…`accent6` become the theme's text, background and accents.
- The major and minor Latin fonts become the heading and body fonts.

**Slides,** in the deck's order, each with its title (the title placeholder's words) and its notes (the notes slide's body).

**Shapes on a slide** (`p:sp`):

- A text box (`txBox="1"`, or no fill and no line) becomes a text box.
- Anything else becomes a shape. Preset geometries map to ours where they match (rectangle, rounded rectangle, ellipse, triangle, right triangle, diamond, pentagon, hexagon, octagon, star 5, arrows, line). Others become a rectangle and are listed in the report.
- Fills: solid colours, as theme references where the deck uses scheme colours; gradients with their stops. Lines: colour and width.
- Rotation and flips.
- A placeholder with no position of its own takes its layout's, else its master's.

**Text:**

- Paragraphs, runs, line breaks and bulleted or numbered lists.
- Bold, italic, underline and strikethrough; size, colour and font.
- Paragraph alignment.

**Pictures** (`p:pic`) are imported into the project's media, with their crop. A picture's description becomes its alt text, and a picture marked decorative stays decorative.

**Tables** (`a:tbl` in a graphic frame) become tables: their cells' text, the header row, and cell fills.

**Groups** (`p:grpSp`) become groups. Each child is placed through the group's child-space transform.

**Not readable in part A,** each listed in the report and kept as a labelled placeholder rectangle where it was:

- charts;
- SmartArt;
- embedded objects (OLE);
- ink;
- 3D models;
- media (sound and video come in part C).

Part D turns the placeholders into pictures.

**The report:** each item says which slide, what, and what was done (imported, approximated, or a placeholder). It is shown after the import, and it can be copied.

**In the editor:** File → Import PowerPoint…, and an "Import PowerPoint…" button on the Welcome screen. Both go through IPC `project.importPowerPoint` (main shows the open dialog, reads the deck, imports its pictures and returns the project and the report). The words are in the string catalogue (P10.4).

**Tests:** decks are built in the tests, in the shape PowerPoint writes. There is no copy of PowerPoint here, and nothing is copied from real decks. Each mapping above has a unit test. The e2e imports a deck through File → Import PowerPoint… and checks its slides, text, picture, table, notes and report.

## Part B: masters, layouts and backgrounds (`wp/p11.1b-pptx-masters`)

- The deck's slide masters and layouts become ours, with their placeholders and their own shapes.
- Each slide uses its layout.
- Slide, layout and master backgrounds: solid colours, gradients and pictures.

## Part C: animations, transitions and media (`wp/p11.1c-pptx-motion`)

- **Entrance and exit effects** that match ours (fade, fly in, wipe, zoom and the like) become ours, with their order, delays and durations.
- **Motion paths** become motion paths.
- **Emphasis effects** and anything else are listed in the report.
- **Slide transitions** that match ours become ours, and the others the nearest, listed.
- **Sound and video** go through the media pipeline (P6.3).

**As built (session 89):**

- **Our motion is a timeline; PowerPoint's is clicks.** The main sequence is laid on the slide's timeline as if every click came at once:
  - an effect started by a click begins when everything before it has ended;
  - "with previous" starts with the effect before it;
  - "after previous" starts when that effect ends;
  - each with its own delay.

  The report says once per slide that click-started animations play in order. The timeline grows to hold them.

- **An entrance sets when its object appears, and an exit when it leaves.** Appear is timing only.
- **Effect ids:** Fly In (with its direction), Fade, Split, Wipe, Circle, Zoom and Bounce are mapped as PowerPoint numbers them. Wheel, and two ids taken as Float, are reported as approximations, because their mapping could not be checked against PowerPoint here. Anything else is a fade, reported.
- **A motion path** keeps its ends and corners (a curve's control points are not places the object goes), as a line or a freeform.
- **Transitions:** a newer transition's exact duration (`p14:dur`) is read; otherwise its speed. One we lack falls back to the deck's own fallback, else a fade, reported.
- **Sound and video:** a stand-in is left, then replaced once the file has been through the pipeline. A file in a format courses do not use (H.264, AAC on Linux) stays a placeholder, and the report says to convert it.

## Part D: LibreOffice, only what the import needs (`wp/p11.1d-pptx-pictures`)

- **`npm run fetch:libreoffice`,** like `fetch:ffmpeg`:
  - downloads a pinned LibreOffice build for the platform and checks its SHA-256;
  - keeps only what a headless conversion of a presentation to pictures needs: the core, Impress, the OOXML filters, charts and drawing, the picture exporters, a basic font set, and the licence and notice files;
  - drops Writer, Calc's UI, Base, Math, help, templates, galleries, dictionaries, other UI languages, Java, Python and extensions.
  - **A smoke test proves the trim:** it converts a small deck with a chart, SmartArt and text to pictures, and the fetch fails loudly if that does not work.
  - The trimmed size for each platform is measured and recorded in `docs/licences.md`.
- **Use:** for each placeholder left by part A, the importer makes a one-slide deck holding just that content, has LibreOffice draw it, and puts the picture where the content was. The report says so.
  - When LibreOffice is missing (a build without the fetch), the placeholders stay, and the report says why.
- **Packaging:** electron-builder ships the trimmed folder as an extra resource, as with ffmpeg.
- **Found while studying the trim (session 90, Windows):**
  - **The build:** LibreOffice 26.8.3, the current stable release. Its download checksums are published by The Document Foundation (`<file>.sha256` beside each file):
    - Windows x64 MSI, 376 MB, `0e6918c2…bf94`;
    - Linux x64 deb tarball, 221 MB, `e7cd3538…dcabf`;
    - macOS x64 dmg, 310 MB, `bb3c35d6…d159`;
    - macOS arm64 dmg, 300 MB, `de943203…b988`.
  - **Unpacking without installing:** on Windows, `msiexec /a … /qn TARGETDIR=…`, an administrative extract that needs no rights and installs nothing. It comes to 1,605 MB.
  - **The smoke deck** (`fixtures/libreoffice/smoke.pptx`, made by `test-deck.ts`): a title, a bar chart with cached values, and SmartArt with PowerPoint's fallback drawing.
    - It is converted headless, with its own throwaway profile, to PNG and SVG.
    - The SVG must contain "Smoke test", "March" (the chart's axis) and "Stop" (the SmartArt), so the check sees what was drawn, not just that a file appeared.
    - The full build takes about 6 seconds and draws all three.
  - **What may go:**
    - `share/` extensions, galleries, templates, wizards, autotext, Basic, scripts, PDF import and Firebird; the icon-theme zips; other languages' registry files;
    - `program/resource` (the interface in 123 languages: English is built in), Python and its core, Java's classes, the shell extension and wizards;
    - help and the readmes;
    - the DLLs of Writer, Calc, Math, Base, the .NET and Java bridges, update checking, migration, jump lists, SharePoint and ActiveX support, and PDF import.
  - **What must stay, though it looks removable:** `mergedlo.dll` links CoinMP, the Firebird client, the Java VM access and framework, lp_solve and orcus (and orcus-parser) at load time. Without them LibreOffice does not start (`0xC0000135`).
    - A small reader of each DLL's import table (written for the study) finds such links. The fetch script checks the same, so a new version cannot quietly break the trim.
  - **Result on Windows:** 443 MB in the study, about 28 % of the full build. The smoke test passes, and its picture is the same as the full build's.
- **Found on Linux (session 90, WSL):** the deb tarball's 42 packages unpack to 731 MB.
  - The same kinds of file go, under Linux names, and also the GTK, Qt and KDE interface plug-ins (headless needs none), the Calc solver's libraries and the Firebird client.
  - Here `libmergedlo.so` links only two of the six that must stay on Windows, the Java VM access and framework; orcus stays because the dialogs library (`libcuilo.so`) links it.
  - The trimmed build's picture of the smoke deck is byte for byte the full build's.
  - It uses the system's cairo, fontconfig, freetype, X11, NSS, D-Bus, GLib and CUPS, which desktop Linux has.
- **Licence:** LibreOffice is MPL 2.0. Its licence and notices travel with it, and `docs/licences.md` gains an entry.

**As built (session 90):**

- **The fetch** (`scripts/fetch-libreoffice.mjs`): download (or `--archive=` a download already on disk), check the SHA-256, unpack, then copy everything not on the platform's drop list into a staging folder.
  - Windows: the MSI's administrative extract. The Visual C++ runtime the installer would put in Windows is copied into `program/`. The fonts the installer would add to Windows are left out.
  - Linux: each `.deb` is read as an `ar` archive by the script itself, and its `data.tar.xz` unpacked with `tar`, so `dpkg` is not needed.
  - **The link check** reads every kept program's and library's imports (PE import and delay-import tables; ELF `DT_NEEDED`) and fails if any names a library that was dropped. It caught `pyuno.pyd` loading Python on its first run.
  - **The smoke test** draws `fixtures/libreoffice/smoke.pptx` to SVG (which must hold "Smoke test", "March" and "Stop") and to PNG, with the export the app uses. A unit test proves the fixture is the test builder's `smokeDeck()`.
  - Only then does the staging folder become `vendor/libreoffice/<os>-<arch>`, with `SOURCE.txt`. On any failure nothing is put there, and the script says why.
  - **Sizes:** Windows 402 MB of 1,605 MB; Linux 365 MB of 731 MB.
  - **macOS:** not yet. The dmg needs `hdiutil` and a trim list of its own, made and checked on a Mac; until then the script says so and exits, and charts stay placeholders there.
- **The drawing** (`drawing.ts`, `drawingDeck`): a copy of the deck with one slide, the size of the content, holding only the content.
  - The content is at the top left, its own size, unturned (the picture object keeps the turn), and without its placeholder link.
  - The slide has no background and shows nothing of its layout or master, whose shape trees are emptied (their theme and text styles kept).
  - Only the parts the presentation reaches are kept, so another slide's video is not copied once per chart. SmartArt's drawing, which its data names through the slide's relationships, is kept.
- **The runs** (`libreoffice.ts`, `drawDecks`): LibreOffice draws to PNG with a transparent background, with a throwaway profile.
  - **A set width.** Left to itself, LibreOffice draws at the screen's density: twice the size on this Windows machine (scaled 200 %), the size itself on headless Linux. So the width is given (`PixelWidth`; the height follows the slide's shape).
  - That width holds for every deck in a run, and a run costs seconds to start (about 1 to 3 s on Windows, 7 s on WSL, whether or not the profile is new). So drawings are grouped by width, each group within a factor of √2 (`widthGroups`). Each group is one run, at twice its widest; every picture comes out between 2 and 2.8 times its frame's width. No side passes 4,096 pixels.
- **The import:** each picture takes its stand-in's place, id, name, timing, animations and description; the report says "drawn as a picture" (approximated).
  - Content LibreOffice cannot read comes back as a fully transparent picture; `isBlankPng` finds that, and the placeholder stays, reported.
  - Without LibreOffice, or when it fails to start or takes too long, the placeholders stay and the report says why.
- **Where it looks:** `VEDRAOPUS_LIBREOFFICE_DIR`, then `resources/libreoffice` when packaged, then `vendor/libreoffice/<os>-<arch>`.
- **Found on the way:** part C's sound and video lost their stand-in's animations when the file came through; they keep them now.

## Part E: LibreOffice for macOS (`wp/p11.1e-libreoffice-mac`, session 102)

Luke asked for it before the Phase 11 review. It was made and checked in the headless macOS VM (`skills/macos-vm.md`), on its `full` image (macOS 26.3, x86_64). The lite image lacks AVFoundation, which LibreOffice links, so it cannot run it.

- **The download:** the x64 dmg, checksum as published.
  - It is mounted read-only and hidden (`hdiutil attach -nobrowse`), the app copied out (`ditto`), and the image detached.
  - The full build draws the smoke deck headless over SSH.
- **The trim:** the same kinds of file as on Windows and Linux, under the bundle's names (`Contents/Resources`, `Contents/Frameworks`), plus the Quick Look and Spotlight plug-ins.
  - As on Windows, `libmergedlo.dylib` loads the Calc solver's libraries, the Firebird client, orcus and the Java glue, so they stay.
  - Two links pointed at what was dropped (Firebird's `intl` files and the Java bridge's `.jnilib`): the script now removes any link left dangling.
- **The link check** reads Mach-O load commands (`LC_LOAD_DYLIB` and its kinds, universal files too). It runs only on macOS: 0xCAFEBABE also starts Java class files, and on Windows it tripped on one.
- **Re-signing:** removing files breaks the bundle's seal (`a sealed resource is missing or invalid`). The script re-signs it ad hoc (`codesign --force --deep -s -`) and checks `codesign --verify --deep --strict`. A release signs it with the Developer ID when the app is packaged.
- **Size:** 715 MB of 1,450 MB (the files' sizes; macOS keeps them compressed, and `du` shows 413 MB).
- **Packaging:** `electron-builder.yml` ships `vendor/libreoffice/mac-${arch}` on macOS.
- **The arm64 build** is pinned but not checked: the VM is x86_64.
