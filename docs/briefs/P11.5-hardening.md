# P11.5 Hardening

**Plan:** "Performance budget (200-slide project opens in under 3 s and edits at 60 fps on a mid-range laptop), large-asset handling, crash reporting (opt-in), telemetry off by default."

The package is built in three parts, each on its own branch. The plan's box is ticked after part C. There is no saved-format change.

## Part A: the performance budget (`wp/p11.5a-performance`)

**The budget, as tests that fail when it is broken:**

- **Opening:** a project of 200 slides opens in under 3 seconds. It is timed from choosing the file to the slide list showing all 200 slides and the stage drawn.
  - The project is made by the test from the model's factories: each slide has a title, body text, two shapes, a picture and a button with a trigger. That is about what a real course has.
- **Editing at 60 frames a second:** while an object on such a project's slide is dragged across the stage, the time between frames is measured in the page (`requestAnimationFrame`).
  - The median must be within one 60 Hz frame (17 ms).
  - The 95th percentile must be within two frames (34 ms), so a dropped frame now and then is allowed, but not stutter.
  - The same is checked while typing into a text box.
- **This machine is the measure.** There is no "mid-range laptop" here. The test records its numbers in its output, and each session log records them. A budget missed on this machine is a bug to fix. If CI's runners in December are slower, their limits are to be set from what they measure, not by loosening these.

**Fixes:** whatever the measurements show. The work is to measure first, then fix the slowest thing, then measure again. Each fix gets a test or a measurement that proves it.

**As built (session 96):**

- `e2e/performance.spec.ts` builds the 200-slide course from the model's factories, with the two-slides fixture's picture. It prints its numbers, and checks that the drag really moved the panel and the typing really landed in the text, so the frames measured are real editing.
- **Measured** (Windows 11 on this machine; WSL Ubuntu headless on the same):

  |                     | Windows       | Linux (WSL)   |
  | ------------------- | ------------- | ------------- |
  | Open 200 slides     | 624 ms        | 475 ms        |
  | Drag: median, p95   | 16.7, 16.8 ms | 16.7, 16.8 ms |
  | Typing: median, p95 | 16.7, 17.4 ms | 16.7, 16.7 ms |

- **No fixes were needed:** the editor already meets the budget with room to spare, so part A is the guard that keeps it so.

## Part B: large media (`wp/p11.5b-large-media`)

Media files can be large: an hour of video, a 100-megapixel photograph.

- **Importing** reads files as streams; nothing large is held in memory whole. A test imports a file of several gigabytes (made sparse, so it takes no real space) and checks memory stays within bounds.
- **Playing in the editor:** the app's media scheme answers range requests, so a long video seeks without the whole file being read.
- **Saving:** the project file is written as a stream, media stored without compression, and a full disk fails cleanly. The old file is untouched and the author is told.
- **Large pictures:** a picture far larger than the stage could ever need is kept as it is, but drawn in the editor from a copy scaled to twice the stage's size, so the stage stays fast. The published course is not changed by this.

**As built (session 97):**

- **Importing** already streamed: hashing and copying never hold a file whole. A unit test imports half a gigabyte (made with `ftruncate`) and checks the process's memory grows by under 128 MB.
- **The media scheme** (`protocol.ts`):
  - it answers `Range` requests with `206` and `Content-Range`, a bad range with `416`, and gives `Accept-Ranges` and `Content-Length` always;
  - it streams from the file instead of fetching it whole;
  - it remembers each asset's file name instead of listing the folder for every request.

  `parseRange` is its own module (`range.ts`), tested without Electron.

- **Large pictures:**
  - the editor asks for `?fit=<twice the stage's longer side>` when a picture's own size is larger than that (`editorAssetUrl`);
  - main makes the scaled copy once with Electron's `nativeImage`, keeps it in the workspace's `previews/` folder (never saved in the project file), and serves it.

  The stage, slide list, overview, media list and handouts use it. The published course uses the file itself.

- **A failed save:**
  - the save is written beside the target and renamed over it only when complete (as before), so the file on disk is unchanged;
  - the editor now says so ("The project could not be saved: …"), where before the failure went unreported.

## Part C: crash reports and no telemetry (`wp/p11.5c-crash-reports`)

- **Crash reports, opt-in and kept on this machine:**
  - with Settings → "Keep crash reports" ticked (off by default), Electron's crash reporter writes a report when the app or a window crashes;
  - **nothing is uploaded** (`uploadToServer: false`);
  - Help → Show Crash Reports opens the folder, so the author can send one if they choose.
  - Sending reports to a server is **Luke's decision**: it sends data off the machine, and needs somewhere to send it.
- **Telemetry: none, and proved.** Vedra Opus has never had telemetry. An e2e goes through a typical session (new project, a slide, a picture, preview, publish to a folder) and records every request the app makes. None may leave the machine: only the app's own files and schemes.
  - **Exceptions, by design:** a web object's page, a link the author opens, and `npm run fetch:*` downloads at build time. None of these is in that session.

**As built (session 98):**

- **The setting** is `keepCrashReports` in the app's own `settings.json` (not the project file): off by default, and off again if the value is damaged or missing.
  - It is read before the app is ready (`crash-reports.ts`), and the crash reporter starts then with `uploadToServer: false`.
  - Help → Keep Crash Reports changes it from the next start, and says so; Help → Show Crash Reports opens `app.getPath('crashDumps')`.
- **The proof of the setting:**
  - the e2e crashes the editor's window on purpose (`forcefullyCrashRenderer`);
  - with the setting off, no report is written;
  - after turning it on and starting again, a report is written, unsent.
- **The proof of no telemetry:**
  - the e2e records every request of the editor's and the preview's sessions while it adds a text box, previews the project and publishes it to a folder;
  - the app's own schemes appear, so requests were seen;
  - nothing is `http`, `https`, `ws` or `ftp`.
- Main makes no network requests of its own. Its only external calls open the author's browser on a link they chose (the repository, a link in a course).
