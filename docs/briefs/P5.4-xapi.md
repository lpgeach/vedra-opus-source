# P5.4 xAPI

**Work package:** P5.4, needs P5.1 (done). Builds on the driver interface and `startCourse` (`P5.2-scorm-12.md`, `P5.3-scorm-2004.md`).

Luke agreed (session 31) that a published course may send learner data to the LRS it is launched with. That is the purpose of xAPI. Tests use an in-repo mock LRS only, and nothing is sent anywhere else.

## Where the code lives

- **In the course:** `packages/player/src/lms/xapi.ts` holds the launch parameters, statement building, the statement queue and the State API. `startCourse` takes `lms: 'xapi'` and `activityId`. Since P5.5 these live in `lrsDriver`, shared with cmi5; `xapiDriver` is `lrsDriver` with the xAPI profile (`P5.5-cmi5.md`).
- **At publish time:** `packages/publish/src/xapi.ts`. `publishXapi(project, { activityId?, ... })` writes the web course plus `tincan.xml`. The default activity id is `urn:vedraopus:course:<project id>`. It is stable across republishing, so an LRS keeps one record per course.

## Launch

The LMS opens `index.html` with query parameters (the common "Tin Can launch" convention):

| Parameter      | Use                                          | Notes                                                                                                          |
| -------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `endpoint`     | LRS base URL                                 | A trailing `/` is added if missing.                                                                            |
| `auth`         | The `Authorization` header value, sent as is | Never logged.                                                                                                  |
| `actor`        | JSON Agent                                   | The older form with arrays (`"mbox": ["mailto:…"]`, `"name": ["…"]`) is accepted and turned into the 1.0 form. |
| `registration` | UUID for this attempt                        | Sent in every statement's context and on State API calls. Optional.                                            |
| `activity_id`  | The course's activity IRI                    | Default: the one written at publish time.                                                                      |

If `endpoint` or a usable `actor` is missing, the course plays untracked and says so in the console, like the SCORM drivers when they find no API.

## Statements

Every statement has:

- an `id` (UUID v4 from `crypto.getRandomValues`; `randomUUID` is unavailable on `file://` and plain `http`) and a `timestamp` taken when the event happened;
- the launch actor;
- `context.registration` when one was given;
- `context.contextActivities.parent` (the course) for slide and interaction statements;
- `version: "1.0.0"` is left to the LRS. The request header `X-Experience-API-Version: 1.0.3` is sent.

| When                                               | Verb                | Object                                                                                                               | Result                                   |
| -------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Tracking starts (after state is loaded)            | `initialized`       | the course                                                                                                           |                                          |
| Each slide entered, the first included             | `experienced`       | the slide: `<course id>/slides/<slide id>`, type `http://id.tincanapi.com/activitytype/slide`, its title as the name |                                          |
| A question answered (P7 calls `recordInteraction`) | `answered`          | `<course id>/interactions/<id>`, type `cmi.interaction`, with `interactionType`                                      | `response`, `success`, `duration`        |
| Completion first becomes completed                 | `completed`         | the course                                                                                                           | `completion: true`                       |
| Success becomes passed or failed (or changes)      | `passed` / `failed` | the course                                                                                                           | `success`, plus the score if one was set |
| Leaving                                            | `terminated`        | the course                                                                                                           | `duration` (ISO 8601), `completion`      |

Names are language maps keyed `en-US`, since the project has no language setting yet.

Status statements are sent on a change only. The status already reached is stored in the state document, so a learner who resumes a completed course does not send `completed` again. A learner who starts over and completes again does send it again, because that is a new completion.

## Queue and retry

- Statements go into an in-memory queue. `commit()` (each slide change, each status change) sends everything queued in one `POST statements`. A retry is safe because the ids are fixed: the LRS accepts a batch it already has.
- **Network failure, `429` or `5xx`:** keep the batch and retry after 1, 2, 4… seconds (at most 30), and send anything queued meanwhile with it.
- **Any other `4xx`:** the batch will never be accepted. Drop it and warn, so one bad statement cannot block the rest.
- **On leaving:** the last state and the queue are sent with `fetch(…, { keepalive: true })`, so they survive the page closing. Browsers allow about 64 KB in flight for keepalive requests. Nothing that sends more is tried.
- **Not in this package:** keeping unsent statements in browser storage for the next visit.

## Resume (State API)

- **One state document**, `stateId=vedraopus.session`, keyed by activity, agent and registration. It holds JSON: `{ "v": 1, "data": "<suspend-data codec text>", "location": "3", "status": { "completion": …, "success": … } }`. The codec is the one SCORM uses, with no size limit. Saving is a `PUT`, which replaces the document.
- **Before the course mounts**, the driver `GET`s the document, showing "Loading…" while it waits.
  - `200`: resume, under the course's resume rule, exactly as for SCORM.
  - `404` or an empty document: a fresh start.
  - Error or no answer within 8 seconds: start fresh, warn, and **do not write state this session**. A slow LRS must not cost the learner their saved progress. Statements are still sent.
- To allow this, `LmsDriver` gains `ready?(): Promise<void>`, which loads what the getters then answer, and `slideEntered?(slide)`. The SCORM drivers need neither.

## Done when

- **Playwright against a mock LRS.** The mock runs on another port, so the CORS preflight is exercised, and it checks auth and version headers. Each test validates every statement's shape:
  - id, actor with exactly one identifier, verb, object, timestamp, registration, context parent;
  - the order: initialized, experienced per slide, completed, terminated with a duration.
- Resume in a second session from the State API.
- Retry after the LRS fails, with no duplicates.
- A completed learner's resumed session does not send `completed` again.
- Untracked without launch parameters.
- **Unit tests:**
  - launch parsing (old actor form, missing parts);
  - UUID form;
  - the retry rules (which statuses retry or drop, and the backoff);
  - status-statement transitions;
  - `tincan.xml` (escaping, activity id, launch file).

## Not in this package

cmi5 (P5.5), zip output and the publish UI (P5.6), quizzes producing scores and answers (P7), statement signing, `tincan.xsd`, keeping queued statements across visits, and fetching the actor from an LMS's own launch API.
