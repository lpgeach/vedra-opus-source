# P5.3 SCORM 2004

**Work package:** P5.3, needs P5.2 (done). Builds on the driver interface, suspend-data codec and `startCourse` described in `P5.2-scorm-12.md`; read that first.

## Where the code lives

- **In the course:** `packages/player/src/lms/scorm2004.ts`, the SCORM 2004 driver. API discovery is shared with SCORM 1.2 (`find-api.ts`). `startCourse` takes `lms: 'scorm2004'` and `edition: 2 | 3 | 4`.
- **At publish time:** `packages/publish/src/scorm2004.ts`: `publishScorm2004(project, { edition, ... })` writes the web course, `imsmanifest.xml` and (for the 2nd and 4th editions) the schema files. `scorm2004Manifest(project, title, files, edition)`. The default edition is the 4th.

## Editions

| Edition | `schemaversion`    | Suspend data limit | Schema files                |
| ------- | ------------------ | ------------------ | --------------------------- |
| 2nd     | `CAM 1.3`          | 4,000 characters   | shipped                     |
| 3rd     | `2004 3rd Edition` | 64,000             | **not shipped** (see below) |
| 4th     | `2004 4th Edition` | 64,000             | shipped                     |

The run-time API is the same in all three. The manifest's namespaces are the same, and the schema files differ. The 2nd edition is a manifest variant: the only run-time difference is its smaller suspend-data limit.

**Schema files** are the "no metadata" sets from Rustici's schema bundles (CC BY 3.0), kept as strings in `scorm2004-schemas.ts`. Identical files are stored once. The source and each original file's SHA-256 are in the file's header.

The 3rd-edition sequencing schemas (`imsss_*.xsd`) carry an IMS notice: anyone who distributes them must first register with IMS and receive a licence. Vedra Opus would be distributing them in every package. Luke decided (2026-11-17) not to register, so 3rd-edition packages have no schema files and no `xsi:schemaLocation`. Most LMSs do not read them, and the 4th edition, the default, has its own.

## Manifest

- One organization with one item, pointing to one SCO resource (`adlcp:scormType="sco"`, `href="index.html"`) that lists every course file. The schema files are not part of the SCO.
- **Simple single-SCO sequencing:**
  - On the item, `imsss:deliveryControls completionSetByContent="true" objectiveSetByContent="true"`. The course reports its own status, so the LMS must not mark it complete just because it was launched.
  - On the organization, `imsss:controlMode choice="true" flow="true"`.
  - Also on the item, `adlnav:presentation` hides the LMS's own previous and continue buttons, since the course has its own navigation.
  - No objectives, rollup rules or navigation requests.

## Run time (`API_1484_11`)

1. **Find `API_1484_11`** the same way as 1.2's `API`: up `parent` (at most 500 frames), then `opener` and its parents.
2. **`Initialize("")`.** Read `cmi.entry`, `cmi.suspend_data`, `cmi.location`, `cmi.completion_status`, `cmi.success_status`. If the completion status is `unknown` or `not attempted`, set it to `incomplete`.
3. **Status** (`setStatus`):
   - `cmi.completion_status` ← `completion`.
   - `cmi.success_status` ← `success` (`passed`, `failed` or `unknown`).
4. **Bookmark** is `cmi.location`. **Suspend data** is `cmi.suspend_data`, encoded as for 1.2, with the edition's limit.
5. **Score** (P7 calls it):
   - `cmi.score.raw`, `cmi.score.min`, `cmi.score.max`.
   - `cmi.score.scaled` = (raw − min) / (max − min), clamped to −1…1 and rounded to 7 decimal places. It is left out when max equals min.
6. **Interactions** (P7 calls them), at `cmi.interactions.n.*`:
   - `id`: a URI as 2004 requires. Ids that are not URIs become `urn:vedraopus:interaction:<id>`, with characters a URN cannot hold replaced.
   - `type`, `learner_response`, `correct_responses.0.pattern`.
   - `result`: `wrong` is written as 2004's `incorrect`.
   - `latency` as an ISO 8601 duration.
   - Response formats differ between the standards (for example, choice lists are separated by `[,]` in 2004). The driver passes responses through unchanged; P7 formats them when it has structured answers.
7. **On leaving:**
   - `cmi.session_time` as an ISO 8601 duration (`PT1H2M5.46S`, rounded to hundredths first).
   - `cmi.exit`: `suspend` while incomplete, else `normal`.
   - Then `Commit`, then `Terminate`.
   - No `adl.nav.request`: a single SCO has nowhere to go next.
8. Every call's error code is checked, and a failure is a warning, never an error thrown into the course.

## Completion never goes backwards (both standards)

There are three ways a learner who has already completed a course can return to a fresh engine:

- the LMS starts a new attempt;
- the learner picks "Start over";
- the course's resume setting is "never".

Each time the engine begins at "not complete", and the next save would tell the LMS `incomplete`, which overwrites the earned completion.

Both drivers now remember the status the LMS gave at start-up and any finished status they have written since, and never write a lower one:

- **SCORM 1.2:** no `incomplete` over `completed`, `passed` or `failed`.
- **SCORM 2004:** no `incomplete` over a completed `completion_status`, and no `unknown` over a `passed` or `failed` `success_status`.

Passed can still become failed and the other way round. Quizzes (P7) decide when that is right.

## Done when

- A Playwright test plays a published SCORM 2004 (4th edition) package inside an in-repo mock `API_1484_11` LMS. It asserts:
  - the call sequence;
  - `completion_status` and `success_status` on completion;
  - `exit`;
  - ISO session time;
  - resume in a second session;
  - that a completed learner who starts over is not marked incomplete.
- Unit tests:
  - API discovery;
  - ISO duration format;
  - scaled score;
  - interaction ids and results;
  - status that never goes backwards, for 2004 and for 1.2;
  - the manifest for each edition: schema version, namespaces, sequencing, files;
  - for the 2nd and 4th editions, each `schemaLocation` names a shipped file with the right `targetNamespace`.
- Each edition's manifest validates with `xmllint` against its schema files. This is a one-off check, recorded in the log, as for 1.2.
