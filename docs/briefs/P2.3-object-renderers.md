# Brief: P2.3 — Object renderers v1

> **Status: implemented 2026-11-15.** Kept for the reasoning. One difference: an image fill is placed by the renderer's own arithmetic when the picture's size is known, because browsers disagree about fitting an SVG picture. `docs/development.md` ("The render package") describes what was built.

Plan entry: `docs/PLAN.md` section 8, P2.3. Depends on P1.1 (done).

## Goal

`packages/render` turns objects from the project model into what a browser draws: shapes, images, buttons and groups, looking the same in the editor, in preview and in a published course, in every browser engine.

## How it is built

1. **One pure function, a plain-data result.** `renderObject(object, context)` returns a `RenderNode`: `{ tag, attrs, style, children }`. Nothing in it touches the DOM, so it runs anywhere and its output can be checked in ordinary unit tests.
2. **Thin back ends turn that into something real.**
   - `toMarkup(node)` → an HTML string (escaped). For thumbnails, published pages and tests.
   - `toDom(node, document)` → DOM nodes. For the player.
   - The editor (P2.2) maps the same tree to React elements, so React can update the stage efficiently. That adapter lives in the app, so `render` and the player stay free of React.
3. **Every object has the same wrapper**: an absolutely positioned box at the object's frame, rotated about its centre, carrying `data-object-id`. Opacity and shadow are applied to the wrapper, so they work the same for every type.
4. **The caller supplies the surroundings** in a `RenderContext`: the theme (to resolve theme colours), `assetUrl(hash)` (the editor and a published course load media from different places), asset metadata, and an `idPrefix` so the same slide can appear twice in one page (stage and thumbnail) without clashing SVG ids.

## Decisions

- **Shapes are SVG paths** inside the wrapper. One path builder per geometry kind; all return a path in the object's own pixel box.
- **Lines and arrows** run along the horizontal centre of the frame, left to right; rotation gives the direction. The arrow head is sized from the outline width and takes the outline colour. A line with no outline draws nothing.
- **Triangles** are isosceles with the point at the top centre.
- **More shapes and callouts are polygon presets** (diamond, pentagon, hexagon, octagon, star, right triangle, parallelogram, trapezoid, chevron, block arrow, plus, speech callout). They are data in `packages/model/src/shapes.ts`, expressed with the existing `polygon` geometry, so the saved format does not change.
- **Gradient angle**: degrees clockwise; 0 runs left to right, 90 top to bottom. Endpoints are computed in pixels so the angle is true on non-square shapes.
- **Image fill** covers the shape, centred, cropping the overflow.
- **Outline dashes** scale with the outline width (dash: 3 on, 2 off; dot: round dots, 2 apart).
- **Shadow** uses a CSS `drop-shadow` on the wrapper, so it follows the shape's outline, not its box.
- **Images** fill their frame. A crop selects the part of the source that is shown, stretched to the frame. There is no separate "fit" setting: the editor sets the frame to the picture's proportions when it is inserted (P2.2). An image whose file is missing draws a neutral placeholder, not the browser's broken-image icon.
- **Buttons** are a rounded rectangle with the button's appearance and a centred label.
- **Groups** are a zero-size wrapper holding their children, whose frames are already in stage units. A group's own rotation is not applied; rotating a group rotates its children's frames (P2.2).
- **Text is provisional.** Proper rich text is P2.4. Until then text boxes, shape text and button labels draw their plain text in the theme's body font, through one function (`renderTextBlock`) that P2.4 replaces.
- **States are not applied here.** `renderObject` draws the object's normal look. Applying a state's overrides arrives with states (P4.1).
- **Object factories** (`createShapeObject`, `createImageObject`, `createButtonObject`, `createTextObject`, `createGroupObject`) are added to `model`, since tests here and the Insert commands in P2.2 both need them.

## Tests

- **Unit (Vitest, no browser):** path geometry, gradient endpoints, crop arithmetic, colour and theme resolution, id prefixing, escaping in `toMarkup`, every preset is a valid polygon.
- **Visual (Playwright, Chromium + Firefox + WebKit):** one screenshot per case — each geometry kind, each fill kind, outline styles, shadow, opacity, rotation, image with and without crop, missing image, button, group. All three engines are compared with **the same** committed reference image, within a small tolerance for edge smoothing. That is what proves "the same everywhere". Reference images are generated with Chromium on Linux.
- Visual tests contain no text, because fonts differ between systems; text snapshots come with P2.4 and its bundled fonts.
- Visual tests have their own config (`playwright.render.config.ts`, `npm run test:visual`) and run in CI on Linux only, where the three browsers are installed by a workflow step.

## Out of scope

Putting renderers on the editor stage (P2.2), rich text (P2.4), format controls (P2.5), states (P4.1), animation (P6).

## Done when

Visual snapshot tests for each type pass in Chromium, Firefox and WebKit (the plan's line).
